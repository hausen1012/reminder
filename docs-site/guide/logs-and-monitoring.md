# 日志与监控

## 日志页

每一次提醒触发都会产生一条日志。日志是不可变的快照，记录的是**触发那一刻**的标题与渲染后正文，
因此即使之后修改或删除提醒，历史记录依然完整。

### 一条日志包含什么

| 字段 | 说明 |
|---|---|
| 触发时间 | 实际开始投递的时间 |
| 标题 / 内容 | 触发瞬间的快照（已渲染占位符） |
| 状态 | `pending` / `success` / `partial` / `failed` / `expired` |
| 已确认 | 需要确认的提醒是否被点击确认 |
| 确认链 ID | 同一轮触发的多次重发共享此 ID |
| 重发轮次 | `0` 表示首次触发，`>0` 表示第 N 次重发 |
| 来源 | `web` / `ai` / `api` |
| 异常说明 | 仅在日志没能正常走到终态时出现，解释原因（见下方「卡住的日志」） |

### 卡住的日志

投递是异步的：触发时先写一条 `pending` 日志，再由后台任务把它推进到终态。
如果进程恰好在投递中途退出（重启、OOM、被强制杀死），这条日志就永远停在 `pending`。

兜底扫描器会处理这种情况：**超过 10 分钟仍是 `pending` 的日志会被标记为 `failed`**，
并写入一条异常说明（如「投递未完成（进程可能中途退出），已由兜底扫描标记为失败」）。
10 分钟远大于单通道最坏重试链（约 1 分钟），不会误判正在重试的投递。

### 通道级明细

展开一条日志可以看到每个通道的**每一次尝试**：尝试序号、状态、耗时、错误信息。
即使通道后来被删除，日志里依然保留当时的通道名称与类型。

### 查询与清理

日志页支持按**状态**、**来源**与**关键字**（标题或内容）筛选，
也可以从提醒详情跳转查看某条提醒的日志。

清理方式有三种，都在日志页操作：

| 方式 | 说明 |
|---|---|
| 删除 7 天前 | 保留最近一周 |
| 删除 30 天前 | 保留最近一个月 |
| 全部清空 | 清掉所有日志 |

清理前会先显示待删除条数做二次确认。也可以勾选指定条数批量删除。

自动清理：设置 `LOG_AUTO_PURGE_DAYS` 大于 0 后，每天凌晨 3 点按保留天数自动清理一次。

::: tip 日志与提醒是独立的
删除提醒不会删除它的历史日志；日志里会回退显示当时的标题快照。
反之清理日志也不影响任何提醒的调度。
:::

## 监控页

监控页展示调度器与兜底扫描的运行时状态，每 10 秒自动刷新。

| 指标 | 说明 |
|---|---|
| 引擎状态 | 调度器是否运行中 |
| 已注册数量 | 当前在调度器里注册了多少条待触发提醒 |
| 注册明细 | 每条注册项的提醒 ID、标题、调度类型与下次触发时间，可点击跳到提醒详情 |
| 兜底扫描 | 扫描器是否运行中、扫描间隔 |

如果「已注册数量」明显小于已启用提醒数，说明有提醒注册失败了，可以看服务端日志里的
「注册提醒到调度器失败」记录（`error` 级别，带提醒 ID、标题与失败原因）。

## 服务端日志

应用日志默认同时写到标准错误与 `LOG_FILE` 目录下按日期命名的文件（如 `2026-11-03.log`）。

### 格式

默认是给人看的一行一条：

```
[INFO] 2026/11/07 - 20:31:39 | 7bc69bc7850af4d0 | AI 对话完成 provider=openai model=deepseek-v4.1-flash rounds=2 retries=0 drafts=1 truncated=false reply_len=86 user_message="帮我建一个每天九点的提醒"
[WARN] 2026/11/07 - 20:34:41 | 7bc69bc7850af4d0 | AI 请求返回错误 provider=openai model=deepseek-v4.1-flash status=429 msgs=5 tools=6 elapsed_ms=38512 body="{\"error\":{\"message\":\"inference exceeds tpm/rpm limit\"}}" src=internal/llm/openai.go:184
```

- 第二列是本次请求的 `request_id`，与响应头 `X-Request-ID` 相同；同一请求的所有日志都能用它串起来。
- `src`（源码位置）只在 `WARN` / `ERROR` 出现，信息级日志不再带。
- 值里含空格时会加引号，其余不加。

需要接入日志采集（Loki / ELK 等）时设置 `LOG_FORMAT=json` 输出 JSON。

### 级别

用 `LOG_LEVEL` 调整输出级别，默认 `info`。**默认级别下只保留值得看的日志**：

| 级别 | 内容 |
|---|---|
| `error` | SQL 失败、panic、内部错误（5xx 响应）、投递最终失败、调度注册失败 |
| `warn` | 4xx 响应、鉴权失败与限流、单次发送失败与重试、敏感字段解密失败、慢查询（> 500ms）、**耗时超过 1 秒的成功请求**、AI 上游报错 |
| `info` | 启动配置、投递完成汇总、AI 对话开始/完成、登录成功、时区变更、自动清理 |
| `debug` | 每条 SQL、访问日志里的成功请求、投递中间步骤、AI 工具轮次明细、通道发送细节 |

::: tip 成功请求默认不记
面板每 10 秒轮询一次监控接口，若每个 2xx 都记 `info`，一天下来日志里只有轮询记录。
因此访问日志在 2xx/3xx 时降到 `debug`：不关心时看不到，需要排查「请求到底进没进来」时
临时把 `LOG_LEVEL` 调成 `debug` 即可。成功但超过 1 秒的请求仍会以 `warn` 出现。
:::

排查线上问题时常用的两种做法：

```bash
# 只看真正的问题
grep -E '^\[(WARN|ERR)\]' /var/log/reminder/2026-11-03.log

# 追一次请求的完整过程（访问日志 + 业务日志 + AI 上游报错）
grep '7bc69bc7850af4d0' /var/log/reminder/2026-11-03.log
```

### 字段

| 字段 | 说明 |
|---|---|
| `time` / `level` / `msg` | 时间、级别、消息（`src` 仅在 warn 及以上输出） |
| `request_id` | 请求级追踪 ID，独立成列，与响应头 `X-Request-ID` 相同 |
| `method` / `path` / `route` / `status` / `latency` / `bytes` | HTTP 访问日志 |
| `user_id` / `token_id` | 调用方身份（JWT 用户 / 外部令牌） |
| `error_code` / `error_message` / `field` | 失败请求的业务错误，与接口响应体一一对应；`field` 为空时省略 |
| `error` | 底层错误原因（含请求体解析失败的原始信息），只进日志不进响应体 |
| `reminder` / `log` / `channel` / `attempt` | 投递链路上的提醒 ID、投递日志 ID、通道 ID 与尝试序号 |
| `provider` / `model` / `status` / `body` / `elapsed_ms` / `upstream_request_id` | AI 调用：厂商、模型、上游状态码、上游响应体（截断 1000 字）、耗时 |
| `user_message` / `rounds` / `retries` / `drafts` | AI 对话：用户提问（截断 500 字）、工具轮次、重试次数、生成的草稿数 |

所有凭据（通道密钥、Webhook Authorization、确认链接令牌、令牌明文、AI API Key）都不会写入日志；
需要区分是哪个凭据时只记长度或前缀。AI 请求地址里的 query（如 `?key=sk-xxx`）会被脱敏成 `***`。
`log` 通道是唯一例外——它的用途就是把正文打出来。

### AI 对话出问题时看什么

一次 AI 对话按下面几条日志串（同一个 `request_id`）：

1. `AI 对话开始`——用户问了什么（`msg_len` / `history_turns` / 请求的模型）；
2. `AI 请求返回错误`（上游）——`status`、上游响应体 `body`、耗时；429 通常是限流，
   401/403 是密钥或权限，400 是参数；
3. `AI 对话结束：调用失败`——`round`（第几轮工具调用）、`retries`（已经重试几次）、
   `user_message`（用户原话），以及展开后的上游错误字段；
4. 成功时只有一条 `AI 对话完成` 汇总，工具轮次明细在 `LOG_LEVEL=debug` 下才会出现。

## 健康检查

```bash
curl http://localhost:8765/api/health
```

```json
{
  "code": 200,
  "message": "ok",
  "data": {
    "status": "healthy",
    "db_alive": true,
    "db_reminders": 12,
    "db_delivery_logs": 340,
    "scheduler": { "running": true, "registered": 10, "last_fire_at": "2026-07-01T09:00:00+08:00" },
    "sweeper": { "running": true }
  }
}
```

**状态码本身就是结论**：数据库可连且调度器运行中时返回 `200` + `status: "healthy"`；
数据库不可用或调度器已停止时返回 `503` + `status: "unhealthy"`（此时 `code` 也是 `503`）。
监控系统直接按 2xx / 5xx 判断即可，不需要解析响应体。

兜底扫描器是否运行单独记在 `data.sweeper.running`，不改变整体结论——
它停掉时仍会返回 `200`，因为主调度器还在工作；想连这一层一起盯，就额外判断该字段。

这个接口不需要认证，可以直接接到监控系统做存活与业务指标采集。

## 兜底补发

系统有两套触发路径：

1. **主调度器**：正常的定时触发，精确到秒
2. **兜底扫描器**：每 `SWEEP_INTERVAL_SEC` 秒扫描一次，找出「下次触发时间已经过去但还没触发」的提醒

兜底扫描解决的是进程重启、机器休眠、时钟跳变等导致主调度器漏掉的触发。它有两个结果：

| 情况 | 处理 |
|---|---|
| 漏触发时间在容忍窗口内 | 立即补发 |
| 漏触发时间早于容忍窗口 | 标记为 `expired`，不再发送，下次触发时间向前推进 |

容忍窗口由 `MISS_TOLERANCE_MINUTES` 控制，默认 60 分钟。

两条路径共用乐观锁，因此同一时刻不会重复触发同一条提醒。

## 重启后的恢复

除了补发漏掉的触发，进程启动时还有两项恢复动作：

| 恢复对象 | 做法 |
|---|---|
| 未完成的确认重发链 | 每个提醒只恢复**最新**那条链；按已发轮次与上次发送时间重排下一轮，停机时间已超过重发间隔的，启动后立即补一轮。链里任一轮已确认、令牌已过期、提醒已禁用/删除的都不恢复 |
| 卡在 `pending` 的日志 | 见上方「卡住的日志」，由第一轮兜底扫描收敛为 `failed` |

因此重启不会让「需要确认」的提醒变成只发一次：只要还没确认、还没用完重发次数，
重启后仍会按原来的节奏继续催。
