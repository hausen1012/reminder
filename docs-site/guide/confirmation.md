# 确认机制

普通提醒发出即结束。开启「需要确认」后，提醒发出会附带一个链接，只有你点了链接才算真正处理完；
在没确认之前，系统会按配置反复重发。

适合「必须确保我真的看到」的场景：吃药、关火、重要待办。

## 开启方式

在提醒里勾选「需要确认」，并填两个参数：

| 参数 | 限制 | 说明 |
|---|---|---|
| 重发间隔 | 最小 60 秒 | 每轮重发之间的等待时间 |
| 最大重发次数 | 至少 1 | 用完之后停止重发 |

也可以让 [AI 助手](/guide/ai-assistant)用对话开启：「这个提醒需要确认，重试 3 次，间隔 60 秒」。
助手会把这三个字段一起写进待确认草稿，确认后效果与在表单里勾选完全一致。

## 一次完整流程

1. 到达触发时间，系统发送提醒，正文带上确认链接 `https://<BASE_URL>/c/<token>`
2. 同时创建一条**确认链**，把这个提醒的这轮触发标记为一组
3. 你点击链接 → 该链路的所有日志标记为已确认，后续重发全部取消
4. 你没点击 → 等待「重发间隔」后再次发送（复用同一个链接，链接不会失效）
5. 重发次数用完后，链路终止，日志停留在未确认状态

每轮重发都会新增一条日志记录（`重发轮次` 字段递增），它们共享同一个确认链 ID，
在日志页会折叠成一组，不会刷屏。

## 确认链接

- 路径是 `/c/:token`，**不需要登录**，方便在手机上直接点
- 使用 32 字节随机令牌，不可猜测
- 有效期 72 小时，超过后点击会提示链接已过期
- 只能真正消费一次：重复点击（连点、刷新、多台设备同时打开）不会报错，而是显示「之前已确认」
  并给出首次确认时间；重复点击不会改写确认时间
- 每个确认链复用同一个令牌，所以重发不会导致旧链接失效

::: warning 链接域名取决于 BASE_URL
确认链接是用 `BASE_URL` 拼出来的。如果 `BASE_URL` 填的是 `localhost`，
手机上点开就是空的。部署时务必把它改成外部可访问的地址，见[配置项](/guide/configuration)。
:::

## 与调度器的关系

确认链是独立于调度器的后台任务：

- 提醒被删除、禁用或修改时，该提醒的确认链会被取消，不再重发
- 提醒的规则本身继续正常调度，确认链只影响「这一轮触发要不要继续重发」

也就是说，一个每小时触发的提醒如果每轮都需要确认，那么上一轮的确认链会在新一轮触发时被取消，
只追踪最新的一轮。

### 重启不会打断确认链

重发定时器在进程内存里，但每条链的状态（已发到第几轮、上一次什么时候发的）存在数据库里。
服务启动时会按这些状态重新排下一轮：

- 停机时间**没超过**重发间隔：再等「剩余的那部分时间」；
- 停机时间**超过**重发间隔：启动后立即补发一轮。

以下情况的链不会被恢复：

- 链里任何一轮已经确认（确认后可能还留下一条未确认的重发日志，那不代表你没处理过）
- 已经用完最大重发次数
- 确认链接已过期（链接都点不开了，继续催没有意义）
- 提醒被禁用、删除或关闭了确认

另外，**每个提醒只恢复最新的一条链**。系统的语义是「只追踪最新一轮」：每轮新触发都会
取消旧链，你能点到的也只是最新那条消息里的链接。历史链不会再被恢复成并发催办。

## 常见问题

**为什么重发间隔最小是 60 秒？**
太短的间隔没有意义——你还没来得及看手机，消息就重复了好几遍。60 秒是「有时间拿起手机」的下限。

**确认之后还会再提醒吗？**
不会。确认只是终止当前这一轮的重发链，下一次按调度规则正常触发。

**链接过期了但我确实需要确认怎么办？**
过期后无法再确认，但这一轮的日志仍然保留在日志页，可以看到当时的内容。
下一次触发会生成新的链路。
