# 发送状态与重试

## 触发总状态

每条日志（`delivery_logs.status`）描述一次触发的整体结果：

| 状态 | 含义 | 什么时候出现 |
|---|---|---|
| `pending` | 发送中 | 触发刚发生，投递尚未结束 |
| `success` | 成功 | 所有绑定通道都发送成功 |
| `partial` | 部分成功 | 至少一个通道成功，至少一个失败 |
| `failed` | 失败 | 所有通道都失败，或提醒没有绑定任何可用通道 |
| `expired` | 已过期 | 漏触发时间早于容忍窗口，直接放弃发送 |

`pending` 只在投递过程中短暂出现。如果日志长期停在 `pending`，通常意味着进程在投递中途退出。

## 通道级尝试

每个通道在一次触发中的每次尝试都单独记录（`delivery_attempts`）：

| 字段 | 说明 |
|---|---|
| 尝试序号 | 从 1 开始 |
| 状态 | `success` / `failed` |
| 耗时 | 该次请求的毫秒数 |
| 错误 | 失败原因；成功时为空 |

通道名称与类型会冗余存进日志，因此通道被删除后历史记录依然可读。

## 重试策略

单个通道发送失败时按固定节奏重试：

```
第 1 次：立即
第 2 次：10 秒后
第 3 次：30 秒后
```

三次都失败则该通道判定为失败。

### 什么情况不重试

错误分两类：

| 类别 | 例子 | 处理 |
|---|---|---|
| 可重试 | 网络超时、连接拒绝、对端 5xx | 按上面的节奏继续重试 |
| 永久性 | 鉴权失败、参数错误、对端返回业务错误码非 0、配置缺字段 | 立即停止，不再重试 |

永久性错误意味着「再试也不会成功」，反复重试只会无意义地冲击对端，甚至触发对方的频率限制。

### 通道之间互不影响

多个通道是**并发**发送的，各自独立重试与记录结果。一个通道的失败不会阻塞或取消其他通道。

## 确认重发链

开启「需要确认」的提醒，除了通道级的重试之外，还有一层**跨轮次的重发**：

```
触发 → 发送 → 未确认
        ↓ 等待「重发间隔」
      重发 → 未确认
        ↓ 等待「重发间隔」
      重发 → 未确认 → 用完重试次数，终止
```

每一轮重发都是一条新的日志，它们：

- 共享同一个 `confirm_chain_id`
- `retry_round` 递增（0 是首次触发）
- 复用同一个确认令牌，链接始终有效

一旦确认或达到最大重发次数，整条链路终止。详见[确认机制](/guide/confirmation)。

## 排查失败

日志详情里能看到每个通道每次尝试的具体错误。常见原因：

| 错误特征 | 可能原因 |
|---|---|
| 连接超时 / 拒绝 | 网络不通、端口写错、对端服务不可用 |
| 鉴权失败（401 / 403） | 密码或授权码错误、密钥过期 |
| 业务错误码非 0 | 钉钉 / 企微的 Webhook 地址失效、机器人被移除 |
| 缺少必填字段 | 通道配置不完整，编辑通道时漏填了 |
| 解密失败 | `ENCRYPTION_KEY` 变更过，需要重新填写敏感字段 |
| 没有可用通道 | 提醒没绑通道，或绑定的通道都被禁用了 |

服务端日志里也能看到对应的记录，关键字包括「通道发送失败」「开始投递」「内容渲染完成」。
